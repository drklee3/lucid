## [2026-08-17] query | MVP e2e proven live against `claude -p` subscription auth; `LinearAdapter` implemented

`research-first`-grounded the actual requirements for a working `claude -p` dispatch (docs checked against Claude Code v2.1.23x): headless `-p` sessions always start in Manual permission mode regardless of plan tier (the "Pro/Max/Team defaults to auto mode" behavior is interactive-only), so dispatch was hanging on the first tool call with no flags set. Fixed by passing `--permission-mode auto` explicitly — confirmed to work in non-interactive sessions (a classifier reviews actions instead of skipping review outright, and repeated classifier blocks are documented to skip that action and continue rather than hang, unlike `bypassPermissions`, which Anthropic's own docs scope to "isolated containers/VMs only" and which lucid's git-worktree isolation doesn't literally satisfy). Also corrected block detection: the `rate_limit`/`billing_error`/`oauth_org_not_allowed` signals only ever appear inside `--output-format stream-json` event JSON (the `system/api_retry` event's `error` field), never as literal substrings in plain-text output — `harness::detect_block`'s original substring-scan implementation was replaced with real NDJSON event parsing. `harness::dispatch_with_fallback` also gained `.current_dir(workdir)` (previously unset) and now surfaces the harness's own `session_id`/`is_error`/`result` text from the stream, not just exit status.

Built `tracker::file::FileTracker`, a JSON-file-backed `TrackerAdapter`, so the full dispatch → trace-link → tracker-note loop could be proven without needing Linear credentials yet. Result: `cargo run --example e2e_smoke` (new, gated out of `cargo test` — it hits the real `claude` binary) ran a real subscription-authenticated `claude -p` turn end to end, captured a real session id and dispatch id, and posted the trace-link note to the file tracker. Split `src/main.rs` into a `lucid` lib + thin bin so the example could import the crate's modules.

In parallel, a background agent implemented `LinearAdapter` for real (previously all `todo!()`), grounded directly against Linear's published GraphQL SDK schema rather than from memory — full findings filed to [tracker-adapter.md § `LinearAdapter` implementation notes](architecture/tracker-adapter.md#linearadapter-implementation-notes). Notable: `issueCreate` requires a team id resolved from a short team key Linear's own trait design hadn't accounted for, so `TrackerConfig` gained a `team_key: Option<String>` field rather than changing `TrackerAdapter`'s trait signature; the env var is `LINEAR_API_KEY`.

Net: `cargo build`/`cargo test` (19 passing)/`cargo clippy --all-targets` all clean; the only remaining `todo!()`s are `main.rs`'s daemon-loop handlers (config loading is real now, but nothing calls `Config::load` or wires `FileTracker`/`LinearAdapter` selection together yet) and the reconciliation loop itself (docs/FEATURES.md § Reconciliation loop) — the next real chunk of scope.

## [2026-08-17] query | Reconciliation loop, presence override, and PM wake implemented; `lucid start` is real

Closed the gap from the previous entry: built the actual daemon loop. `Config::load` now really parses TOML (`src/config.rs`, new `DaemonConfig` for tick/timeout/workdir knobs); `tracker::build` selects `FileTracker` vs `LinearAdapter` from `TrackerConfig.backend`. Presence gained an explicit-override layer (`src/presence/override_file.rs`) deliberately *not* implemented as a `PresenceSource` — it's a priority short-circuit (`Active`/`Autonomous` bypass the debounce entirely), not a composable idle signal, which the original design language ("always wins over automatic sources") implied but didn't state precisely; `presence::resolve` is the actual mode-resolution function combining override + sustained-idle debounce. Since `logind`'s real D-Bus wiring is still unimplemented (and known-broken on WSL2 regardless), the daemon runs with an **empty** automatic-source list by default — a deliberate conservative choice (documented at `main.rs::default_presence_sources`) so autonomy today only ever comes from an explicit `lucid presence override autonomous`, not a silent crash from calling an unimplemented source's `is_idle()`.

Built `src/pm.rs` (PM gap-detection wake): dispatches a restricted `--allowedTools` (read-only-ish) harness call, parses a JSON-array response into `Proposal`s, dedups via `query_similar`, files via `create_proposal`, respects a cap and `--dry-run`. Built `src/daemon.rs` (`Daemon::run_foreground`): presence-gated tick loop — dispatch newly-approved issues (retrying `Failed`/`TimedOut`, leaving `Succeeded` alone), then a PM wake once its interval has elapsed. Deliberately **sequential per tick, not a concurrent task-supervisor** — a real spawn-and-poll-across-ticks model was judged more machinery than this pass warranted; stall protection is per-dispatch-timeout, not a separate concurrent stall detector. State is in-memory only (`Daemon.runs`), consistent with `rusqlite` persistence being a separately-deferred item, not silently dropped.

`harness::dispatch_with_fallback` gained a hard timeout + `kill_on_drop(true)` and a `DispatchRequest`/`DispatchError` (`thiserror`) shape — not in the original design, added because an unbounded `cmd.output()` would hang the whole reconciliation tick forever on a stalled harness, which is exactly the dominant real-world failure mode the research pass already flagged. `worker::run_dispatch` and `pm::wake` both go through this; a Worker dispatches under `--permission-mode auto` (full access, classifier-reviewed), a PM wake under an explicit `--allowedTools` read-only list — two different callers needing genuinely different permission surfaces was the reason `DispatchRequest` bundles `claude_extra_args` instead of a single hardcoded mode.

Live-tested the full loop against real `claude -p` subscription auth (not just unit tests): seeded a `proposal:approved` issue in a `FileTracker` store, ran `lucid start --foreground`, watched it dispatch once, mark `Succeeded`, post the trace-link note, and correctly *not* re-dispatch on later ticks. That same live run caught a real bug — PM wake's `last_pm_wake` timestamp was only updated on success, so a failing wake (empty scratch workdir, no git repo to investigate) retried every 5-second tick forever instead of backing off; fixed by recording the attempt before the dispatch regardless of outcome, verified live afterward (one attempt, then correct backoff).

`src/main.rs` fully wired: `start` (foreground; errors clearly on `--foreground`-less detached mode, matching docs/CLI.md's own "not yet designed" admission rather than pretending to support it), `pm wake`, `presence status`/`override`, `config validate`/`show` are all real. `status`/`show`/`stop` remain unimplemented — genuinely blocked on IPC design docs/CLI.md already flags as undecided, not descoped silently. `docs/FEATURES.md` updated checkbox-by-checkbox against what's actually built, including items intentionally not yet done. `cargo build`/`cargo test` (36 passing)/`cargo clippy --all-targets` all clean.
