## [2026-08-17] query | Reconciliation loop, presence override, and PM wake implemented; `lucid start` is real

Closed the gap from the previous entry: built the actual daemon loop. `Config::load` now really parses TOML (`src/config.rs`, new `DaemonConfig` for tick/timeout/workdir knobs); `tracker::build` selects `FileTracker` vs `LinearAdapter` from `TrackerConfig.backend`. Presence gained an explicit-override layer (`src/presence/override_file.rs`) deliberately *not* implemented as a `PresenceSource` — it's a priority short-circuit (`Active`/`Autonomous` bypass the debounce entirely), not a composable idle signal, which the original design language ("always wins over automatic sources") implied but didn't state precisely; `presence::resolve` is the actual mode-resolution function combining override + sustained-idle debounce. Since `logind`'s real D-Bus wiring is still unimplemented (and known-broken on WSL2 regardless), the daemon runs with an **empty** automatic-source list by default — a deliberate conservative choice (documented at `main.rs::default_presence_sources`) so autonomy today only ever comes from an explicit `lucid presence override autonomous`, not a silent crash from calling an unimplemented source's `is_idle()`.

Built `src/pm.rs` (PM gap-detection wake): dispatches a restricted `--allowedTools` (read-only-ish) harness call, parses a JSON-array response into `Proposal`s, dedups via `query_similar`, files via `create_proposal`, respects a cap and `--dry-run`. Built `src/daemon.rs` (`Daemon::run_foreground`): presence-gated tick loop — dispatch newly-approved issues (retrying `Failed`/`TimedOut`, leaving `Succeeded` alone), then a PM wake once its interval has elapsed. Deliberately **sequential per tick, not a concurrent task-supervisor** — a real spawn-and-poll-across-ticks model was judged more machinery than this pass warranted; stall protection is per-dispatch-timeout, not a separate concurrent stall detector. State is in-memory only (`Daemon.runs`), consistent with `rusqlite` persistence being a separately-deferred item, not silently dropped.

`harness::dispatch_with_fallback` gained a hard timeout + `kill_on_drop(true)` and a `DispatchRequest`/`DispatchError` (`thiserror`) shape — not in the original design, added because an unbounded `cmd.output()` would hang the whole reconciliation tick forever on a stalled harness, which is exactly the dominant real-world failure mode the research pass already flagged. `worker::run_dispatch` and `pm::wake` both go through this; a Worker dispatches under `--permission-mode auto` (full access, classifier-reviewed), a PM wake under an explicit `--allowedTools` read-only list — two different callers needing genuinely different permission surfaces was the reason `DispatchRequest` bundles `claude_extra_args` instead of a single hardcoded mode.

Live-tested the full loop against real `claude -p` subscription auth (not just unit tests): seeded a `proposal:approved` issue in a `FileTracker` store, ran `lucid start --foreground`, watched it dispatch once, mark `Succeeded`, post the trace-link note, and correctly *not* re-dispatch on later ticks. That same live run caught a real bug — PM wake's `last_pm_wake` timestamp was only updated on success, so a failing wake (empty scratch workdir, no git repo to investigate) retried every 5-second tick forever instead of backing off; fixed by recording the attempt before the dispatch regardless of outcome, verified live afterward (one attempt, then correct backoff).

`src/main.rs` fully wired: `start` (foreground; errors clearly on `--foreground`-less detached mode, matching docs/CLI.md's own "not yet designed" admission rather than pretending to support it), `pm wake`, `presence status`/`override`, `config validate`/`show` are all real. `status`/`show`/`stop` remain unimplemented — genuinely blocked on IPC design docs/CLI.md already flags as undecided, not descoped silently. `docs/FEATURES.md` updated checkbox-by-checkbox against what's actually built, including items intentionally not yet done. `cargo build`/`cargo test` (36 passing)/`cargo clippy --all-targets` all clean.

## [2026-08-17] query | Worker completion: dispatch prompt was title-only, tracker never closed a task, commit/review policy designed and built

Prompted by "can this be used e2e right now, and how does a Worker actually complete a task" — the honest answer on both counts was worse than expected, and both were real bugs, not just missing scope:

1. **`TrackerIssue` never carried a description at all**, and `daemon::dispatch_approved_issues` passed only `issue.title` to `worker::run_dispatch` — the frontmatter+body handoff surface [Agent handoff](architecture/agent-handoff.md) describes existed in `render_description`'s output but never reached the dispatched harness. Fixed by adding `TrackerIssue.description`, threading it through both `FileTracker` and `LinearAdapter::query_by_label`/`query_similar` (the GraphQL queries were missing the `description` field entirely), and building `worker::dispatch_prompt` to render title-as-heading + description instead of the bare title.
2. **`FileTracker::set_decision_state` never remapped `labels`**, only `decision_state` — and `query_by_label` filters on `labels`. Approving a local-backend issue left it invisible to the dispatch loop forever; the file backend's approval path was silently broken. `LinearAdapter` already did this correctly (add/remove `proposal:*` labels), so the two backends disagreed on the decision surface. Fixed to mirror `LinearAdapter`'s behavior.
3. **Nothing ever verified a "successful" dispatch, and nothing ever closed the tracker item.** "Success" was purely the harness's own `is_error`/exit-code self-report; `acceptance_criteria` was dead data nothing read back; and `DecisionState` had no terminal state at all — a fully successful run left the issue labeled `proposal:approved` forever, with only a comment (the trace-link note) as a signal a human had to go find. Designed and built the fix as [Worker completion](architecture/worker-completion.md): a `CompletionMode` (`None` default / `Commit` — harness commits its own work under an appended prompt instruction, lucid only observes `HEAD` before/after since there's no worktree isolation yet to make a blind `git add -A` safe) and a `ReviewMode` (`Auto` default — daemon sets `DecisionState::Done` itself off the harness's self-report; `Human` — sets a new `DecisionState::NeedsReview` and stops, the first real implementation of the "parked state" rule `docs/FEATURES.md` had flagged as unbuilt; `Agent` — a second read-only dispatch reviews the diff against `acceptance_criteria` and returns a `VERDICT: PASS`/`FAIL` line, fail-open to `NeedsReview` on anything unparseable). Cross-linked into [Review/rework UX](architecture/review-rework-ux.md): that fork assumes a PR exists to act on, which `CompletionMode::Commit` doesn't have — `ReviewMode` is the pre-merge gate instead for that mode, not a replacement for the fork once a `BranchAndPr` mode eventually exists.

Verified live end-to-end, not just via unit tests: `examples/e2e_smoke.rs` rewritten to file a real `Proposal` (with description + `acceptance_criteria` + `ReviewMode::Auto`), approve it, dispatch through the same `query_by_label("proposal:approved")` → `dispatch_prompt` → `run_dispatch` → `finalize_completion` path the daemon uses, against a real `claude -p` subscription session in `CompletionMode::Commit`. Result: the harness read the description, wrote `NOTES.md`, committed it with `LOCAL-1` in the message, lucid observed the new `HEAD` and reported "Committed `45882dfe3eaf`," and `finalize_completion` correctly set `decision_state: Done` — the whole loop closing itself with no human step after approval. `cargo build`/`cargo test` (45 passing)/`cargo clippy --all-targets` all clean.

## [2026-08-17] query | `lucid task` CLI: does a manual approve/dispatch path drift from the tracker as source of truth?

Raised directly in conversation: adding a CLI to approve/dispatch tracker items risked reading as lucid becoming a second, competing source of truth alongside the configured tracker (Linear, or the local file store). Resolved as no drift, with the distinction actually mattering split three ways, not one:

- **`lucid task list`** — pure read via `TrackerAdapter::query_by_label`. Can't drift; it's a rendering of the tracker's current state, nothing more.
- **`lucid task approve`/`reject`** — calls `TrackerAdapter::set_decision_state`, the identical call the tracker's own UI action makes (for Linear: the same `issueAddLabel`/`issueRemoveLabel` mutations a human clicking the label dropdown would trigger). This *converges* with the tracker rather than drifting from it — there's one state, and this is just another writer of it, the same way `gh issue close` doesn't compete with GitHub's own UI as a source of truth.
- **`lucid task dispatch-now <id>`** — the one case where drift was a real risk, avoided by requiring the target issue already be `Approved` in the tracker (errors out otherwise, pointing at `lucid task approve`). It changes *when* approved work runs — immediately, instead of waiting for the next presence-gated tick — never *whether* it's allowed to. Same authority check the daemon's own tick loop already does, just invoked on demand instead of on a timer.

Built accordingly: extracted `worker::dispatch_and_finalize` (build prompt → `run_dispatch` → `finalize_completion`) so `daemon::dispatch_approved_issues` and `lucid task dispatch-now` share the *exact* code path rather than two implementations that could drift from each other over time. Added `lucid task list/approve/reject/dispatch-now` (`src/cli.rs`, handlers in `src/main.rs`) — no `--review` override on approve; `ReviewMode` is still only set at proposal-filing time, not currently updatable from the CLI. Live-tested against the file backend end-to-end: seeded a pending issue, `list` (empty for `approved`), `approve` (now visible), `dispatch-now` under `CompletionMode::Commit` — harness wrote the file, committed it, `finalize_completion` marked it `Done`, all from three CLI calls with no hand-edited JSON. Documented in `docs/CLI.md` (new `lucid task` section) and cross-linked from `docs/wiki/architecture/worker-completion.md`. `cargo build`/`cargo test` (45 passing, unchanged — no new tests added by this change)/`cargo clippy --all-targets` all clean.

Also brought up Arize Phoenix locally via `docker compose up -d` (operational, not a design decision — no wiki page) to watch trace output while testing; confirmed the OTLP endpoint reachable and a dispatch's trace-link URL resolves against it.

## [2026-08-17] query | Traces were never actually exporting — two separate bugs, one environmental, one real

Follow-up to the previous entry's "confirmed... trace-link URL resolves against it": resolving is not the same as containing the right data, and pushing further surfaced two distinct problems.

**Bug 1, environmental, not lucid's fault:** a stray host-level process — `uv tool run arize-phoenix serve --host 127.0.0.1 --port 6006`, started two days earlier for unrelated work — was already bound to port 6006. `docker compose up -d` for the `phoenix` service reported success without erroring (Docker doesn't reliably detect a bare host socket the way it detects another container's port claim), but `localhost:6006` kept resolving to the stray process's own unrelated projects (`evals-sandbox`, `evals-naive`, etc.) instead of the new container — confirmed by querying the container's own live SQLite db directly (`docker exec lucid-phoenix-1 python3 -c "import sqlite3; ..."` against `/mnt/data/phoenix.db`, which showed only an empty `default` project) versus what `localhost:6006` served (the unrelated projects). Fixed by killing the stray process and `docker compose restart phoenix` so the container's own port binding took effect. Documented as a gotcha on [Trace correlation](architecture/trace-correlation.md).

**Bug 2, real, in `harness::apply_telemetry` (`src/harness/mod.rs`):** even with the port fixed, a fresh dispatch produced 0 spans and 0 traces. Ground-truthed against [Claude Code's own OTel docs](https://code.claude.com/docs/en/monitoring-usage) (`research-first`, since this depended on Claude Code's current telemetry config surface, not something to trust from memory): `CLAUDE_CODE_ENABLE_TELEMETRY=1` + `OTEL_LOGS_EXPORTER=otlp` only exports the *logs* signal — distributed tracing (spans) is a separate, off-by-default beta feature requiring both `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1` and `OTEL_TRACES_EXPORTER=otlp`, neither of which `apply_telemetry` had ever set. This means [Trace correlation](architecture/trace-correlation.md)'s whole mechanism — the trace-link posted back to every tracker item — had never actually had spans behind it to link to, since the feature was designed. Added both missing env vars; re-ran the same dispatch and got 2 spans / 1 trace, with the span's `lucid` resource attribute (`{dispatch_id: ..., ticket_id: ...}`) confirmed to exactly match the `dispatch_id` already posted in the tracker note. Trace correlation is now verified working end-to-end for Claude Code specifically — Codex's export completeness was not re-checked and stays designed-not-confirmed, noted on the page.

`cargo test` still 45 passing (no new tests added — this was an env-var fix with no new branch to unit-test; verification was live, against a real Phoenix instance), `cargo clippy --all-targets` clean.
