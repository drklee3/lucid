## [2026-08-17] query | Reconciliation loop, presence override, and PM wake implemented; `lucid start` is real

Closed the gap from the previous entry: built the actual daemon loop. `Config::load` now really parses TOML (`src/config.rs`, new `DaemonConfig` for tick/timeout/workdir knobs); `tracker::build` selects `FileTracker` vs `LinearAdapter` from `TrackerConfig.backend`. Built `src/pm.rs` (PM gap-detection wake): dispatches a restricted `--allowedTools` (read-only-ish) harness call, parses a JSON-array response into `Proposal`s, dedups via `query_similar`, files via `create_proposal`, respects a cap and `--dry-run`. ## [2026-08-17] query | Worker completion: dispatch prompt was title-only, tracker never closed a task, commit/review policy designed and built

Prompted by "can this be used e2e right now, and how does a Worker actually complete a task" — the honest answer on both counts was worse than expected, and both were real bugs, not just missing scope:

1. **`TrackerIssue` never carried a description at all**, and `daemon::dispatch_approved_issues` passed only `issue.title` to `worker::run_dispatch` — the frontmatter+body handoff surface [Agent handoff](architecture/agent-handoff.md) describes existed in `render_description`'s output but never reached the dispatched harness. Fixed by adding `TrackerIssue.description`, threading it through both `FileTracker` and `LinearAdapter::query_by_label`/`query_similar` (the GraphQL queries were missing the `description` field entirely), and building `worker::dispatch_prompt` to render title-as-heading + description instead of the bare title.
2. **`FileTracker::set_decision_state` never remapped `labels`**, only `decision_state` — and `query_by_label` filters on `labels`. Approving a local-backend issue left it invisible to the dispatch loop forever; the file backend's approval path was silently broken. `LinearAdapter` already did this correctly (add/remove `proposal:*` labels), so the two backends disagreed on the decision surface. Fixed to mirror `LinearAdapter`'s behavior.
3. **Nothing ever verified a "successful" dispatch, and nothing ever closed the tracker item.** "Success" was purely the harness's own `is_error`/exit-code self-report; `acceptance_criteria` was dead data nothing read back; and `DecisionState` had no terminal state at all — a fully successful run left the issue labeled `proposal:approved` forever, with only a comment (the trace-link note) as a signal a human had to go find. Designed and built the fix as [Worker completion](architecture/worker-completion.md): a `CompletionMode` (`None` default / `Commit` — harness commits its own work under an appended prompt instruction, lucid only observes `HEAD` before/after since there's no worktree isolation yet to make a blind `git add -A` safe) and a `ReviewMode` (`Auto` default — daemon sets `DecisionState::Done` itself off the harness's self-report; `Human` — sets a new `DecisionState::NeedsReview` and stops, the first real implementation of the "parked state" rule `docs/FEATURES.md` had flagged as unbuilt; `Agent` — a second read-only dispatch reviews the diff against `acceptance_criteria` and returns a `VERDICT: PASS`/`FAIL` line, fail-open to `NeedsReview` on anything unparseable). Cross-linked into [Review/rework UX](architecture/review-rework-ux.md): that fork assumes a PR exists to act on, which `CompletionMode::Commit` doesn't have — `ReviewMode` is the pre-merge gate instead for that mode, not a replacement for the fork once a `BranchAndPr` mode eventually exists.

Verified live end-to-end, not just via unit tests: `examples/e2e_smoke.rs` rewritten to file a real `Proposal` (with description + `acceptance_criteria` + `ReviewMode::Auto`), approve it, dispatch through the same `query_by_label("proposal:approved")` → `dispatch_prompt` → `run_dispatch` → `finalize_completion` path the daemon uses, against a real `claude -p` subscription session in `CompletionMode::Commit`. Result: the harness read the description, wrote `NOTES.md`, committed it with `LOCAL-1` in the message, lucid observed the new `HEAD` and reported "Committed `45882dfe3eaf`," and `finalize_completion` correctly set `decision_state: Done` — the whole loop closing itself with no human step after approval. `cargo build`/`cargo test` (45 passing)/`cargo clippy --all-targets` all clean.

## [2026-08-17] query | `lucid task` CLI: does a manual approve/dispatch path drift from the tracker as source of truth?

Raised directly in conversation: adding a CLI to approve/dispatch tracker items risked reading as lucid becoming a second, competing source of truth alongside the configured tracker (Linear, or the local file store). Resolved as no drift, with the distinction actually mattering split three ways, not one:

- **`lucid task list`** — pure read via `TrackerAdapter::query_by_label`. Can't drift; it's a rendering of the tracker's current state, nothing more.
- **`lucid task approve`/`reject`** — calls `TrackerAdapter::set_decision_state`, the identical call the tracker's own UI action makes (for Linear: the same `issueAddLabel`/`issueRemoveLabel` mutations a human clicking the label dropdown would trigger). This *converges* with the tracker rather than drifting from it — there's one state, and this is just another writer of it, the same way `gh issue close` doesn't compete with GitHub's own UI as a source of truth.
- **`lucid task dispatch-now <id>`** — the one case where drift was a real risk, avoided by requiring the target issue already be `Approved` in the tracker (errors out otherwise, pointing at `lucid task approve`). It changes *when* approved work runs — immediately, instead of waiting for the next presence-gated tick — never *whether* it's allowed to. Same authority check the daemon's own tick loop already does, just invoked on demand instead of on a timer.

Built accordingly: extracted `worker::dispatch_and_finalize` (build prompt → `run_dispatch` → `finalize_completion`) so `daemon::dispatch_approved_issues` and `lucid task dispatch-now` share the *exact* code path rather than two implementations that could drift from each other over time. Added `lucid task list/approve/reject/dispatch-now` (`src/cli.rs`, handlers in `src/main.rs`) — no `--review` override on approve; `ReviewMode` is still only set at proposal-filing time, not currently updatable from the CLI. Live-tested against the file backend end-to-end: seeded a pending issue, `list` (empty for `approved`), `approve` (now visible), `dispatch-now` under `CompletionMode::Commit` — harness wrote the file, committed it, `finalize_completion` marked it `Done`, all from three CLI calls with no hand-edited JSON. Documented in `docs/CLI.md` (new `lucid task` section) and cross-linked from `docs/wiki/architecture/worker-completion.md`. `cargo build`/`cargo test` (45 passing, unchanged — no new tests added by this change)/`cargo clippy --all-targets` all clean.

Also brought up Arize Phoenix locally via `docker compose up -d` (operational, not a design decision — no wiki page) to watch trace output while testing; confirmed the OTLP endpoint reachable and a dispatch's trace-link URL resolves against it.

## [2026-08-17] query | Commit observation was single-SHA (dropped multi-commit work); direct-commit-to-shared-directory named as an anti-pattern by current practice

Prompted directly by a question about how `CompletionMode::Commit` actually works and what happens if the harness wants to make several commits — the honest answer at the time was "it doesn't handle that." `worker::describe_commit_result` compared `git rev-parse HEAD` before/after dispatch and reported a single SHA; if the harness made two or three commits (one per logical change), only the last one's SHA would ever show up in the tracker note, with no count and no indication multiple commits happened at all.

Ran a `research-first` pass to ground how autonomous coding agents actually complete tasks in git before redesigning around a guess. Findings, cited to their actual sources rather than asserted from memory:

- **Aider auto-commits after every file edit by default** (<https://aider.chat/docs/git.html>, fetched and read directly) — specifically so `/undo` can cleanly revert one step at a time. Multiple commits per task is the *normal* case for at least one widely-used agentic coding tool, not an edge case worth deprioritizing.
- **Orchestrators track agent commits by listing everything ahead of a base ref** (`git log <base>..HEAD --oneline`), not a single before/after SHA compare — the exact mechanism the old `describe_commit_result` was missing.
- **"Never let an agent commit to a shared branch — every task gets its own feature branch/worktree"** turned up as a converging rule across GitHub Copilot coding agent, Cursor background agents, and multi-agent orchestrator write-ups (buildmvpfast, addyosmani.com's "Code Agent Orchestra") — search-result-level corroboration, not deep-fetched primary sources the way the Aider docs were, and flagged as such rather than overstated.

Read together, this reframed `CompletionMode::Commit`'s no-worktree, shared-`daemon.workdir`, direct-commit design: it's not just "a smaller version of branch+PR," it's the specific thing current practice names as unsafe, independent of whether a PR happens afterward. lucid's human-approves-every-task bootstrap phase substitutes for PR *review*, but not for worktree *isolation* — two dispatches, or a dispatch overlapping local edits, can still collide in the same directory. Documented as a deliberate, now-explicit tradeoff (not an oversight) on [Worker completion](architecture/worker-completion.md), which also raises the practical priority of per-issue worktree isolation in `docs/FEATURES.md`.

Fixed the actual bug: added `worker::commits_since` (`git log --oneline <before>..HEAD`), rewrote `describe_commit_result` to report every commit instead of one SHA, and loosened `dispatch_prompt`'s instruction from "commit your changes" to explicitly "one commit or several, whatever's logically right for the change." Added a new test (`commit_mode_reports_every_commit_not_just_the_last`) exercising a two-commit dispatch and asserting both commits' messages show up in the tracker note; updated the existing single-commit test's assertion to match the new "N commit(s):" format. `cargo test`: 46 passing. `cargo clippy --all-targets`: clean.

## [2026-08-17] query | Deterministic `verify_cmd` gate for `ReviewMode::Agent`

Follow-on design question, prompted directly by the user: "how does the agent signal it's done — does that just rely on the agent following the prompt?" Traced through what's actually structural vs. prompt-trust today: the *process-ended-without-erroring* signal (Claude Code's `stream-json` `result` event's `is_error`) is real and not gameable by omission, but *task correctness* — whether a commit happened, whether `ReviewMode::Agent`'s `VERDICT:` line reflects reality — was entirely prompt-trust, mitigated only by failing open to `NeedsReview` rather than defaulting to `Done`. The user then asked specifically how a set of required deterministic checks would be configured without becoming tedious per-repo/per-task setup, which is what this entry resolves.

Decision, made with the user before implementing: lucid runs the verify command itself and checks the real exit code, rather than widening the review agent's tool access and trusting its own report of whether tests passed — an exit code is a fact, an LLM's summary of one is a claim. Config-tedium was resolved by making `verify_cmd` optional rather than required: unset, the review agent infers its own command from the repo's conventions (`Cargo.toml`/`package.json`/`CLAUDE.md`) the way a human contributor would; set, it pins an exact command. Storage reuses the existing frontmatter surface rather than adding new tracker-adapter plumbing: `verify_cmd` can't be a label the way `review` is (free text, not a small enum), so it's read back via a new `tracker::frontmatter_field(description, key)` parser — a narrow, explicit exception to "lucid doesn't re-parse the frontmatter text," documented on both [Agent handoff](architecture/agent-handoff.md) and [Worker completion](architecture/worker-completion.md).

Implementation: `Proposal.verify_cmd: Option<String>`, rendered into `render_description`'s frontmatter; `worker::run_verify_cmd` runs it via `sh -c` with a timeout and returns the exit status; wired into `finalize_completion`'s `ReviewMode::Agent` branch ahead of `agent_review` — a failing or unspawnable verify command short-circuits straight to `NeedsReview` with a note, and the LLM review dispatch never runs at all. Added 4 `frontmatter_field` unit tests and 2 `finalize_completion` tests covering both the short-circuit and pass-through paths (the short-circuit test uses empty harness profiles deliberately — if verify_cmd's failure hadn't actually prevented the review dispatch, the call would hit `DispatchError::NoProfiles` and return `Err` instead of the asserted `Ok`).

Live-verified against a real `claude -p` dispatch, not just unit tests: a failing `verify_cmd` (`exit 1`) correctly parked the issue at `NeedsReview` without ever invoking the review agent; a passing one (`test -f PING.txt`) correctly proceeded to a real review dispatch. That live run also surfaced a genuine, worth-noting characteristic rather than a bug: the reviewer's restricted `--allowedTools` (`Bash(git diff *)`/`log *`/`status *` only) `permission_denied`-blocked a compound Bash command the model tried, which ended that turn without a parseable `VERDICT:` line — correctly routed to `NeedsReview`, not a false `Done`. Rerunning the identical prompt manually produced a clean `VERDICT: PASS` immediately after, consistent with ordinary model non-determinism rather than a systemic issue with the gate itself. `cargo test`: 52 passing. `cargo clippy --all-targets`: clean.

## [2026-08-17] query | `verify_cmd` resolved through three tiers, not just per-task; grounded against Symphony and Copilot

Two rounds of user pushback on the `verify_cmd` design above, both real gaps:

1. "Wouldn't per-task `verify_cmd` mean writing the same command into every proposal?" — for most repos it's one command, true for every task (`cargo test`), so per-task-only was pushing config to the wrong layer. Fixed by adding `daemon.verify_cmd: Option<String>` in `lucid.toml` (`DaemonConfig`) as a repo-wide default — set once, same shape as a CI config.
2. "Would this mean maintaining a separate set of verification, or can it just execute existing commands? CI reuse only works for PRs, which lucid doesn't have" — correct on both counts: lucid has no worktree/branch/PR flow yet, so literally reusing `.github/workflows/*.yml` the way GitHub Copilot coding agent does isn't buildable today. Fixed by adding `worker::detect_verify_cmd`, an auto-detection tier that reads the repo's own already-existing convention instead of requiring any new config: `Cargo.toml` present → `cargo test`; `package.json` with a `scripts.test` entry → `npm test` (the project's own defined script, not a guess); `Makefile` with a `test:` target → `make test`.

`worker::resolve_verify_cmd` now checks, in order: task-level frontmatter override → `daemon.verify_cmd` → auto-detected convention → `None` (review agent infers). The common repo needs zero config at either explicit tier.

## [2026-08-17] query | Decision state moves the real Linear ticket state, not a label

First real setup of the Linear backend surfaced a design flaw the file-backend-only development had hidden: `DecisionState` was purely a `proposal:*` label on the Linear issue, never touching the issue's actual `state` field — invisible to Linear's board view, filters, and any state-based automation. For a system whose stated point is controlling a task through a real project tracker rather than a bespoke store, tracking state on the side in a label defeats that purpose: a human looking at the board sees nothing of lucid's decisions.

Three designs were weighed: (a) map onto Linear's built-in `type` category (`backlog`/`unstarted`/`started`/`completed`/`canceled`) for minimal setup, but `Approved` and `NeedsReview` have no native type equivalent; (b) a hybrid — real state for the four concepts that map to a `type`, label only for the two that don't; (c) six explicitly named workflow states owned by lucid (`Pending`, `Approved`, `In Review`, `Done`, `Rejected`, `Stale`), looked up by name per team, mirroring the `review:*` label setup already required. Exact GraphQL shapes were confirmed by introspecting the live schema rather than assumed from memory or docs: `WorkflowStateFilter` has `name`/`team` fields shaped identically to the existing `IssueLabelFilter`, `IssueFilter.state` exists for `{state: {name: {eq}}}` filtering, and `workflowStateCreate`/`issueUpdate` are the real mutations. ## [2026-08-18] ingest | Worktree-isolated PR dispatch replaces direct-commit completion

Prompted by a design discussion about scaling to parallel/automated dispatch: with the prior direct-commit design, every dispatch committed straight into the shared `daemon.workdir`, so a second dispatch (or a dispatch overlapping local edits) could collide in the same directory, and there was no real review/merge surface — `ReviewMode::Human`/`Agent` were the entire gate, with nothing to click through and nothing to revert cleanly. Discussed and resolved: give every dispatch a real PR, even at today's sequential (one-issue-at-a-time) dispatch concurrency, since PR-based completion is valuable independent of parallelism — it's what makes worktree isolation itself possible (a shared directory can't safely `git add -A`), and it gives `Auto`/`Agent`-pass a real merge step instead of a bare state transition.

Built: `src/worktree.rs` (`create`/`remove` — a `lucid/<issue-id>` branch off `daemon.base_branch`, checked out under `daemon.worktree_root`, deliberately outside `daemon.workdir`) and `src/pr.rs` (`push_branch`/`create`/`merge`, thin wrappers over `git push` and `gh pr create`/`gh pr merge --squash --delete-branch`). `worker::dispatch_and_finalize` now creates the worktree, dispatches the harness there, pushes+opens a PR for whatever it committed, decides a `ReviewVerdict` (`CloseAutomatically`/`NeedsHuman`) per `ReviewMode` while the worktree is still alive, tears the worktree down, and only then closes out the tracker item — merging the PR itself for `CloseAutomatically`, leaving it open for a human otherwise. `CompletionMode` (`None`/`Commit`) is removed entirely; `daemon.completion_mode` in `lucid.toml` is replaced by `daemon.base_branch` (default `"main"`) and `daemon.worktree_root`.

An adversarial code-review pass (`/code-review high`) on the initial implementation found three real correctness bugs before this shipped, all fixed and covered by new regression tests: (1) retrying a `Failed`/`TimedOut` dispatch reused a branch name that `worktree::remove` deliberately leaves behind, so `worktree::create` failed forever with "branch already exists" — fixed with `git worktree prune` + `git branch -D` before re-adding; (2) a dispatch that committed real work but failed to push/open a PR was indistinguishable from "no changes at all" (`Option<PullRequest>` was `None` either way), so it silently read back as `Done` — fixed with `PrOutcome::{NoChanges, Created, Failed}`, routing `Failed` to `NeedsReview`; (3) the merge (`gh pr merge --delete-branch`) ran while its branch was still checked out in the about-to-be-removed worktree, which can make `gh`'s own cleanup fail — fixed by splitting the review decision (`decide_review`, runs before teardown) from the merge/`DecisionState` transition (`finalize_completion`/`mark_done`, runs strictly after teardown).

Full design detail (worktree lifecycle, PR body/title shape, the three bug fixes, who has merge authority under each `ReviewMode`) is in the rewritten [Worker completion](architecture/worker-completion.md) rather than repeated here; also updated `docs/wiki/index.md`'s summary line and the now-applicable fork framing in [Review/rework UX](architecture/review-rework-ux.md).

## [2026-08-19] query | Sandboxed-by-default execution and multi-project daemon design

Two related questions asked together: how should lucid handle multiple git repos from one running instance, and how should it handle dispatch triggered by someone other than the operator (e.g. a teammate's ticket via the ingestion path in [human-in-the-loop](architecture/human-in-the-loop.md)) without running arbitrary code on the operator's own machine unsandboxed.

`research-first` grounded both before designing anything. For sandboxing: current writing on coding-agent isolation (Shane Deconinck, 2026) states plainly that a VM/container boundary is what makes it safe to let an agent run unattended with broad permissions at all — not a replacement for a permission classifier, the thing the classifier is supposed to sit inside of. Lucid's current dispatch has no such boundary; `--permission-mode auto` alone is carrying weight current practice says shouldn't be carried alone. Also grounded: every naming convention checked (including Claude Code's own `--dangerously-skip-permissions`, already used in this codebase's own dispatch args) gives the *unsafe* option the scary explicit name, never the safe one — settling that sandboxed should become the default once it exists, with bare-host execution as a loudly-named opt-out. For multi-project CLI selection: compared kubectl/Docker's persistent stateful context (whose own issue trackers show recurring user confusion about which context is active) against flyctl's file-discovery and `gh`'s directory-detection patterns — chose directory detection, consistent with how lucid already resolves `lucid.toml` today.

Filed as two pages rather than one: [sandboxed-execution](architecture/sandboxed-execution.md) (where a dispatch runs) and [multi-project](architecture/multi-project.md) (which repo/tracker a dispatch belongs to) — related and cross-referenced (concurrent dispatch across projects depends on both), but genuinely separate concepts per the one-page-per-concept rule. Multi-project design leans on [symphony-patterns](architecture/symphony-patterns.md)'s already-documented `WORKFLOW.md` precedent — repo-owned config checked into the repo, not centralized in the operator's local gitignored file, which `lucid.toml` currently is. Neither page is implemented; both explicitly flag open items (`--cloud`'s actual flag compatibility is unverified, not yet its own research pass; `FileTracker` id-collision across projects untested). Updated `docs/wiki/index.md` with both.

## [2026-08-18] query | Presence gate narrowed: approved dispatch runs every tick

`daemon::tick` (`src/daemon.rs`) moved `dispatch_approved_issues()` out of the `if mode != Autonomous` early return so it runs unconditionally every tick, same as `reconcile_needs_review`. Only `maybe_wake_pm()` stays behind the `Autonomous` gate. Reasoning: an `Approved` issue already has an explicit human decision behind it, so dispatching it isn't the unsupervised-action risk presence-gating exists to guard against — that risk is specifically the PM investigating and filing *new* proposals unattended. `lucid task dispatch-now` is accordingly now a pure tick-interval shortcut, not a presence bypass, since there's no dispatch-side gate left to bypass; updated its description in `docs/CLI.md` and its doc comments in `src/cli.rs`/`src/worker.rs` accordingly.

Added a "What presence gates" section to [presence-detection](architecture/presence-detection.md) stating the new scope explicitly, and two `daemon.rs` unit tests: an `Approved` issue's decision-state query fires during a tick even when presence resolves `Active` (proving the query isn't skipped), and `last_pm_wake` stays unset after an `Active` tick (proving the PM-wake gate is still intact). Both build a `Daemon` directly via struct literal in-test rather than through `Config`/`Daemon::new`, since a real dispatch would need a live git remote and `gh` — out of scope for a unit test.
