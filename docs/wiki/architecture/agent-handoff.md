# Agent Handoff Surface

Same frontmatter-body split as Symphony's WORKFLOW.md (see [Symphony patterns](symphony-patterns.md)), embedded directly in the tracker issue: `task_type`, `target_paths`, `acceptance_criteria` (list), `research_ref` (link to the [Research agent](research-agent.md)'s findings, not re-summarized prose), `review` and `verify_cmd` (see [Worker completion](worker-completion.md)).

Three different mechanisms read this surface — not two — depending on what a field needs:

- **lucid itself parses `review` structurally, via a label, not the frontmatter text.** A `review:auto`/`review:human`/`review:agent` tracker label (Linear label / `FileTracker` field) — `TrackerIssue::review` carries the already-parsed value. `render_description`'s `review:` frontmatter line is there for a human/harness reading the issue, not lucid's own source of truth. This works because `review` has a small, fixed set of values a label can represent.
- **lucid also parses `verify_cmd` structurally, but from the frontmatter text itself**, via `tracker::frontmatter_field`. `verify_cmd` is free text (a shell command) — it can't be a label the way `review` can, so instead of adding a second structural mechanism, lucid re-parses the one scalar field it needs out of the same YAML-ish frontmatter block `render_description` already renders and `description_frontmatter_is_parseable_json_per_field` already proves is machine-parseable. This is a deliberate, narrow exception: a *specific, known key* gets read back by name, not the frontmatter treated generally as lucid-readable data.
- **The dispatched harness** (`worker::dispatch_prompt`) receives `task_type`/`target_paths`/`acceptance_criteria`/`research_ref`/`verify_cmd` as the rendered frontmatter+body block appended to the prompt — an LLM reading structured text, not lucid parsing it back out (except for the one exception above). This is still the intended lever against "worker misinterprets vague proposal": a Worker is handed the same explicit fields every time instead of inferring intent from freeform prose, it just does so by reading them, not by lucid extracting them as data before dispatch.
