# CI and Quality Tooling

Three GitHub Actions jobs on every push/PR (`.github/workflows/ci.yml`: `check` for fmt/clippy/test, `deny` for cargo-deny, `zizmor` for workflow security lint), plus a separate weekly/manual mutation-testing workflow (`.github/workflows/mutants.yml`). Config lives in `deny.toml` and `.cargo/mutants.toml` at the repo root.

## cargo-deny covers advisories; no separate cargo-audit job

`cargo-deny`'s `[advisories]` section reads the same RustSec advisory database `cargo-audit`/`rustsec/audit-check` would, plus it does license and source-registry checks in the same pass. Running both would just double-scan the same advisory data for no extra coverage, so there's deliberately no `rustsec/audit-check` job — `cargo-deny check` (advisories + licenses + bans + sources) is the single tool for all of it.

`deny.toml`'s license allow-list was generated by running `cargo deny init` and then `cargo deny check` against the real dependency tree, not hand-written from memory — the SPDX ids in `[licenses].allow` are exactly what showed up as rejected across the actual tree (MIT, Apache-2.0, ISC, BSD-3-Clause, Unicode-3.0, Unlicense, MIT-0, CC0-1.0, CDLA-Permissive-2.0, Zlib). `lucid` itself has no `license` field (Cargo.toml gained `publish = false` — it isn't going to crates.io, see [tech-stack § Naming note](tech-stack.md#naming-note)), so `[licenses.private].ignore = true` treats it as an unpublished workspace crate rather than tripping the unlicensed check.

Setting this up caught one real, live vulnerability: `h2` 0.4.15 (pulled in via `reqwest`) had [RUSTSEC-2026-0258](https://rustsec.org/advisories/RUSTSEC-2026-0258) (unbounded empty DATA frames, low severity) — fixed by `cargo update -p h2` to 0.4.16, not by suppressing the advisory.

## zizmor: annotations, not the default SARIF mode

The `zizmor` job uses the official `zizmorcore/zizmor-action` with `advanced-security: false, annotations: true` — deliberately *not* the action's SARIF default. Per zizmor's own docs, `--format=sarif` intentionally never exits non-zero on findings (SARIF consumers expect results to live in the SARIF payload, not the exit code), which would make the job always green regardless of what it found. Plain/`--format=github` mode does exit non-zero per finding severity, so that's what actually gates CI.

## Every third-party action is pinned to a commit SHA, not a tag

Tags are mutable; a compromised maintainer token can repoint one without a new commit appearing (this happened to `tj-actions/changed-files` in 2025 — one compromised PAT repointed every version tag at once). Every `uses:` in both workflows pins a full commit SHA with the human-readable version as a trailing comment. `.github/dependabot.yml`'s `github-actions` ecosystem entry is what keeps those SHAs from going stale — without it, a SHA-pinned action never updates on its own.

`dtolnay/rust-toolchain@stable` is the one exception worth naming: it's pinned to the `stable` branch's current HEAD commit, which is a moving target by design (it tracks whatever Rust's current stable release is) — Dependabot bumping that pin is expected and desired, not a drift to fight.

## cargo-mutants: weekly, not per-push

A full `cargo mutants` run rebuilds and re-runs the test suite once per generated mutant, which is too slow to gate a normal push/PR (a `--check`-only dry run against this crate already took ~2 minutes for 216 mutants; a real run with tests is far slower). `mutants.yml` runs it on a weekly `schedule` plus `workflow_dispatch`, uploads `mutants.out` as an artifact, and doesn't block merges.

`.cargo/mutants.toml` excludes `src/main.rs` via `exclude_globs` — it's thin CLI-argument dispatch with no unit tests of its own (see its own doc comment), so mutating it only produces mutants nothing can catch, not real signal.

## First-time `cargo fmt` was a prerequisite, not scope creep

`rustfmt.toml` existed but nothing had ever run `cargo fmt --all -- --check` against the tree — adding that as a CI gate required first running `cargo fmt --all` once across the whole `src/` tree (formatting-only, no logic changes) so the new job wouldn't fail on day one for pre-existing drift rather than a real regression.
