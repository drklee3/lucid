# Worker Completion

How a successful dispatch turns into "this task is done" — and who gets to decide that. Two independent axes, both resolved per-issue rather than per-repo: [worktree + PR completion](#completing-the-working-tree-worktree--pr) (what happens to the working tree) and [`ReviewMode`](#closing-the-tracker-item-who-merges) (who signs off before the tracker item closes).

Before this page existed at all, neither axis did: a "successful" dispatch was just the harness's own `is_error`/exit-code self-report, and nothing ever moved the tracker item out of `Approved` — see [Agent handoff](agent-handoff.md) for the parallel gap that made prompts carry only the issue title, not its description.

## Completing the working tree: worktree + PR

Every dispatch runs in its own git worktree, not the shared `daemon.workdir`:

- **Worktree per issue** (`worktree::create`/`remove`) — a fresh checkout at `daemon.worktree_root/<branch-slug>`, on a new branch `lucid/<issue-id>` (`worktree::branch_name`) created off `daemon.base_branch`'s current tip. `worktree_root` is deliberately outside `daemon.workdir`, so per-issue worktrees never show up in the main repo's own `git status`.
- **The harness commits its own work** — `worker::dispatch_prompt` appends an instruction telling it to `git commit` once it's confident any `acceptance_criteria` are met, explicitly "one commit or several, whatever's logically right for the change," with the issue id required in at least one commit message. It's told **not** to push or open a PR — that's lucid's job now, not the harness's.
- **lucid pushes and opens the PR** (`src/pr.rs`) — `pr::push_branch` (`git push -u origin <branch>`), then `pr::create` (`gh pr create --head <branch> --base <base_branch>`), title = the issue title, body links back to the tracker item id. If the dispatch made no commits, this step is skipped entirely (nothing to push).
- **Cleanup**: the worktree checkout is always torn down (`worktree::remove`, `git worktree remove --force`) once dispatch + review are done, regardless of outcome. It does **not** delete the branch — an unmerged branch (still under review, or the dispatch failed) needs to survive worktree cleanup so its history isn't lost; a merged branch is deleted separately by `pr::merge --delete-branch`.

This replaces the earlier direct-commit-to-shared-directory design (`CompletionMode::None`/`Commit`, no worktree, no PR) that this page originally documented. That design was live-tested and worked, but was flagged in-session as a real, named anti-pattern in current agent-orchestration practice, not just a smaller-scale version of branch-plus-PR: current practice (GitHub Copilot coding agent, Cursor background agents, multi-agent orchestrators generally) treats "never let an agent commit to a shared branch — every task gets its own feature branch/worktree" as a baseline safety rule, not an optional enhancement. Aider's own docs (<https://aider.chat/docs/git.html>) additionally confirmed that commit-per-file-edit (not commit-per-task) is normal agent behavior, which is why `dispatch_prompt`'s commit instruction stayed loose ("one commit or several") rather than assuming exactly one. Per-issue worktree isolation was the blocking dependency for a `BranchAndPr`-style mode; it's now built, and this page describes the result.

### Observing what the harness committed

`worker::commits_since` runs `git log --oneline <head-before-dispatch>..HEAD` inside the worktree, and `describe_commit_result` reports every entry ("N commit(s):" plus each one-liner) in the dispatch note — a harness making several commits per task is normal, not an edge case, so a single before/after SHA compare would silently drop all but the last. Falls back to `git status --porcelain`'s dirty-file count ("Left N file(s) uncommitted — nothing to open a PR for") or "No changes" when nothing landed.

### Three correctness bugs found and fixed before this shipped

An adversarial code review of the initial worktree+PR implementation surfaced three real bugs, all fixed:

- **Retrying a failed dispatch reused a branch name that still existed.** `worktree::remove` deliberately never deletes `handle.branch` (an unmerged branch needs to survive worktree cleanup — see above), so when `daemon::dispatch_approved_issues` retries a `Failed`/`TimedOut` issue on the next tick, `worktree::create` was called again with the identical issue id and failed outright with "a branch named ... already exists." Fixed: `create` now runs `git worktree prune` (clears the stale administrative record for the just-removed directory) then `git branch -D <branch>` (force-deletes any leftover branch) before `git worktree add -b`. Safe to force-delete: the only thing that ever creates `lucid/*` branches is this function, and a prior attempt's commits either already made it into a still-open PR (safe on the remote) or were never pushed at all.
- **A dispatch that committed real work but failed to open a PR could read back as `Done`.** The original code represented "no PR" (either "nothing to merge" or "PR creation failed") as a single `Option<PullRequest>` — `None` either way — so a failed `git push`/`gh pr create` (rejected push, `gh` not authenticated, a PR for that branch already existing) fell through to the same "nothing to merge, mark `Done`" path as a genuinely no-op dispatch. Fixed: `PrOutcome::{NoChanges, Created(PullRequest), Failed}` makes the two cases distinguishable; `mark_done` now routes `PrOutcome::Failed` to `NeedsReview` instead of `Done`, so an unreviewed, possibly-unpushed commit never silently reads back as closed.
- **The merge ran while the branch was still checked out in its own worktree.** The original ordering removed the worktree only *after* `finalize_completion` (which includes the `gh pr merge --delete-branch` call) returned — so at merge time, the branch was still checked out at the worktree path, and `gh`'s own local cleanup for `--delete-branch` can fail when a branch is checked out elsewhere (surfaces as a merge failure, routing the issue to `NeedsReview` even though the PR may have merged fine on GitHub). Fixed by reordering: the merge decision is now split from the review decision. `decide_review` (runs while the worktree is still alive) computes a `ReviewVerdict` (`CloseAutomatically` / `NeedsHuman`) without merging anything; `dispatch_and_finalize` then removes the worktree; only after that does `finalize_completion`/`mark_done` (which performs the actual `pr::merge`) run. The worktree is now guaranteed gone before any merge is attempted.

## Closing the tracker item (who merges)

`Proposal.review` / `TrackerIssue.review` (`ReviewMode`, defaults to `Auto`) — this is the fork [Review/rework UX](review-rework-ux.md) flagged as "still open," resolved as one field instead of a repo-wide policy so a human (or, in phase two, the PM/research layer) can dial trust up or down per ticket. `ReviewMode` now decides what happens to the PR opened above, not what happens to a direct commit:

- **`Auto`** — a `Succeeded` dispatch with a PR is merged immediately: `pr::merge` runs `gh pr merge --squash --delete-branch`, then the issue moves to `DecisionState::Done`. No human gate. lucid is the merge authority here — the same authority it already had to flip the tracker item to `Done` before PRs existed, now expressed as an actual `gh pr merge` call instead of a bare state transition.
- **`Human`** — a `Succeeded` dispatch's PR is left open; the issue moves to `DecisionState::NeedsReview` and stops. A human is the merge authority here, through GitHub's own PR UI — no new UX to build or learn, the worktree that produced the PR was invisible plumbing. The dispatch loop never re-picks a `NeedsReview` issue up on its own (it's out of the `Approved` decision state entirely — for `LinearAdapter` that's the issue's real ticket state, not a label; see [Tracker adapter](tracker-adapter.md#decision-state-the-issues-real-ticket-state-not-a-label)) — a human has to look and flip it back to `Approved` (retry) or forward to `Done` themselves — though the terminal case where the human just merges (or closes) the PR itself is now reconciled automatically; see [Closing `NeedsReview` from the daemon side](#closing-needsreview-from-the-daemon-side-daemonreconcile_needs_review) below.
- **`Agent`** — first, a deterministic gate: if `Proposal.verify_cmd` is set, `worker::run_verify_cmd` runs it (`sh -c`, in the worktree) and checks the exit code *itself* — lucid, not an LLM's summary of whether it passed. A nonzero exit (or the command failing to even run) short-circuits straight to `NeedsHuman` with a note; the review dispatch below never runs at all. If it passes (or `verify_cmd` is unset), a second, read-only dispatch (`worker::agent_review`, same profile list, `pm::wake`'s restricted non-mutating `--allowedTools` surface) reviews the pending diff against `acceptance_criteria` and replies with a single `VERDICT: PASS` / `VERDICT: FAIL: <reason>` line. `PASS` merges the PR exactly like `Auto` above; `FAIL`, an unparseable reply, or the review dispatch itself erroring all route to `NeedsHuman` rather than guessing — fail-open-to-human, never a silent pass.

A merge failure at any point (conflict, unmet branch protection, a required check still pending) is **never retried or resolved automatically** — `mark_done` attaches `gh`'s own error message as a tracker note and routes to `NeedsReview`, leaving the PR open for a human to sort out. This is the closest lucid comes to answering the still-"unsolved industry-wide" merge-conflict question [Review/rework UX](review-rework-ux.md) raises: it doesn't solve conflicts, it just guarantees it never guesses at resolving one itself.

A `Failed`/`TimedOut` run never reaches any of this: `dispatch_and_review_in_worktree` returns `None` for the verdict when `run.phase != WorkerPhase::Succeeded`, so `finalize_completion` is never called and the issue's `DecisionState` stays `Approved` — exactly the state `daemon::dispatch_approved_issues`'s existing retry check looks for.

### Internal split: deciding vs. closing

`decide_review` computes a `ReviewVerdict` (`CloseAutomatically` / `NeedsHuman`) — the `ReviewMode` logic above, including `verify_cmd` and `agent_review` — entirely while the worktree is still alive, since `verify_cmd` and the diff review both need the checked-out files. `finalize_completion` then turns that verdict into an actual `DecisionState` change, including the `mark_done` merge call, and deliberately runs *only after* `dispatch_and_finalize` has torn the worktree down (see the third bug above for why the ordering matters). Nothing outside `worker.rs` needs to know about this split — `dispatch_and_finalize` is still the one function daemon.rs and `lucid task dispatch-now` call.

### `verify_cmd`: deterministic, but deliberately optional — and resolved in two tiers

Prompted by a direct question during design ("how is this configured — doesn't a required per-repo/per-task setting get tedious?"), `verify_cmd` was built as an override, not a requirement. A second round of pushback sharpened this further: per-task-only config means writing the same command into every proposal for a repo where it's always the same string. `worker::resolve_verify_cmd` resolves through two tiers, in order:

1. **Task-level override** — `Proposal.verify_cmd` in the issue's own frontmatter. The exception, not the default path: a docs-only task skipping tests, a monorepo task scoped to one package.
2. **Repo-wide default** — `daemon.verify_cmd` in `lucid.toml` (`DaemonConfig.verify_cmd`). The common case: one command, true for every task in the repo, set once — the same shape as a CI config, just not literally reusing `.github/workflows/*.yml`.

Neither tier set → `None`, same fallback as before `verify_cmd` existed (the review agent infers its own command from the repo).

The task-level tier's write path is `lucid task create --verify-cmd <cmd>` (also `--review`, for the field above) — see `docs/CLI.md`. Before this, setting either field meant hand-editing a ticket's frontmatter text or constructing a `Proposal` struct directly in Rust (`examples/e2e_smoke.rs`). Once filed, neither is updatable from the CLI — `lucid task approve`/`reject` only change decision state.

A third tier — auto-detecting a command from repo conventions (`Cargo.toml` present → `cargo test`, a `package.json` `scripts.test` entry → `npm test`, a `Makefile` `test:` target → `make test`) — was built, then deliberately removed after a third round of pushback: a follow-up question ("would this mean maintaining a separate set of verification, or can it just execute existing commands? CI reuse only works for PRs anyway") first motivated adding it, but the immediate next objection was that guessing a single command from repo shape creates a *false* sense of "verified" — the repo's actual CI might also lint, typecheck, or run several suites the guessed command doesn't cover, and a partial check that looks like a real gate is worse than no gate at all. Resolved as: two explicit config tiers only, no guessing. If neither is set, `verify_cmd` simply doesn't run — the existing LLM-inferred fallback is honestly weaker, not silently narrower.

**Grounded against prior art** (`research-first`, in-session): OpenAI Symphony — the system this repo's own wiki treats as the closest reference (see [Symphony patterns](symphony-patterns.md)) — was checked directly against its actual `SPEC.md`, not a summary. It has **no verification mechanism at all**: the `WORKFLOW.md` frontmatter schema (§5.3) has no test/verify/build field, §2.2 explicitly scopes "business logic for tickets/PRs" out as a non-goal delegated entirely to the workflow prompt, and its own success criterion is soft — *"a successful run can end at a workflow-defined handoff state... not necessarily Done"* (§11.5). GitHub Copilot coding agent doesn't invent a parallel config surface either (this finding is from search results, not a primary-source fetch, so held with less confidence than the Symphony citation): it reuses the repo's actual existing CI, triggered on the PR it opens, gated behind human approval to run plus mandatory human review before merge. lucid's worktree+PR design now matches that shape structurally (a real PR exists to trigger CI against), though lucid doesn't yet trigger or wait on the PR's CI checks itself — `verify_cmd` remains a direct local run, not a CI-gate wait.

This is why the deterministic check only exists for `verify_cmd`'s exit code, not for "did the diff satisfy `acceptance_criteria`" generally — that second judgment stays LLM-based (`agent_review`) regardless, since there's no exit-code equivalent for it. `verify_cmd` closes the part of the gap that has one; it doesn't make the whole `Agent` mode deterministic.

Storage-wise, `verify_cmd` doesn't get the `review` field's treatment (a Linear label lucid parses back structurally) — it's free text, which can't be a label. Instead it's read back via `tracker::frontmatter_field`, which parses one scalar key out of the same frontmatter block `render_description` already renders. This is a deliberate, narrow exception to the pattern [Agent handoff](agent-handoff.md) otherwise documents (frontmatter is for the *harness* to read as prose, not for lucid's own code to re-parse) — justified here because, unlike `review`, there was no label-shaped alternative.

**Live-tested, both branches, against a real `claude -p` dispatch** (not just unit tests, prior to the worktree+PR rework): a failing `verify_cmd` correctly short-circuited before the review dispatch ever ran (confirmed by passing empty harness profiles — if the review path had been reached, it would have hit `DispatchError::NoProfiles` and returned `Err`, but the call returned `Ok`). A passing `verify_cmd` correctly proceeded to a real review dispatch.

Every real `ReviewMode::Agent` dispatch across three separate live-tested tasks returned an empty, unparseable verdict — not occasional flakiness, every single time. Root cause: Claude Code's CLI arg parser can swallow the prompt into a preceding flag's value — specifically, `--allowedTools <list>` (used by both the reviewer and `pm::wake`, never by the Worker's own `--permission-mode auto`) consumes the *next* bare token too, so `--print` sees no prompt argument at all and exits before ever emitting a `result` event. This explains the identical "produced no result text" failures `pm::wake` was also hitting on every real run. Confirmed by direct reproduction (`claude -p --allowedTools "Read,Grep" "prompt"` errors with `Input must be provided either through stdin or as a prompt argument`; the same invocation with a `--` separator before the prompt, or `--allowedTools=Read,Grep`, succeeds normally). Fixed in `harness::dispatch_with_fallback` by inserting `--` before the prompt argument for every Claude Code dispatch, regardless of which flags precede it — this correctly failed open to `NeedsReview` rather than a false `Done` while it was broken, but it was a deterministic parsing bug, not "ordinary LLM non-determinism" as this page previously claimed.

## Closing `NeedsReview` from the daemon side: `daemon::reconcile_needs_review`

Everything above happens inside a single dispatch (`worker::dispatch_and_finalize`). `NeedsReview` itself has no in-process trigger to leave it — the decision is made by a human, on GitHub, outside lucid entirely. Something still has to notice that decision and write it back to the tracker; that's `daemon::reconcile_needs_review` (`src/daemon.rs`), a separate mechanism from anything in `worker.rs`.

The very first thing `Daemon::tick()` does — before presence is even resolved — is query the tracker for every `NeedsReview` issue and look up `pr::status(daemon.workdir, worktree::branch_name(&issue.id))` (`gh pr view <branch> --json state`, `src/pr.rs`) for each. Four outcomes:

- **Merged** → `attach_note` + `set_decision_state(Done)`.
- **Closed** (without merging) → `attach_note` + `set_decision_state(Rejected)`.
- **Open** → left untouched; the human hasn't decided yet.
- **`None`** (no PR found for that branch — `gh` reports "no pull requests found") → left untouched, same as `Open`. `pr::classify_state` maps `gh`'s own `state` field (`"MERGED"`/`"CLOSED"`, else `Open`) — an unrecognized value also falls to `Open` rather than erroring, since this is read-only status that only ever gates whether reconciliation touches the issue.

This runs unconditionally, every tick, regardless of `PresenceMode` — it's placed *before* the `if mode != Autonomous { return }` gate that guards `dispatch_approved_issues`/`pm::wake`. Deliberate, not an oversight: everything gated on presence *dispatches new work* (spends harness budget, and is gated specifically because it shouldn't run unwatched outside an autonomous window); this step only *records a decision a human already made*. There's nothing to gate against — reconciling to `Done` promptly after a human merges is strictly better than waiting for the next autonomous window, and the step itself never touches the working tree or spends harness time.

Before this existed, nothing revisited a `NeedsReview` issue after a human merged its PR by hand — the tracker item sat in `NeedsReview` indefinitely unless a human separately flipped its decision state themselves, bypassing `TrackerAdapter` entirely to do so. lucid still never merges a `NeedsReview` PR itself — that would defeat the point of the human gate above — it only reads the merge status back after the human's own decision, the same "lucid never resolves anything itself, it only asks `gh` and reports back" principle `src/pr.rs`'s own module doc states for the push/merge half.

## Triggering this on demand

`worker::dispatch_and_finalize` bundles "create the worktree, build the prompt, dispatch, push+open a PR, decide the review verdict, tear the worktree down, then close out (and merge) per that verdict" into one call — `daemon::dispatch_approved_issues` uses it on its regular presence-gated tick, and `lucid task dispatch-now <issue-id>` (see `docs/CLI.md`) calls the *identical* function on demand for one issue, instead of waiting for the next tick. It requires the issue already be `Approved` in the tracker and refuses otherwise: the CLI command changes **when** approved work runs, it is never a second authority deciding **whether** work is allowed to run — that decision stays with whatever set the tracker's decision state (a human in Linear, or `lucid task approve`, which itself is just another caller of the same `TrackerAdapter::set_decision_state` the daemon reads back).

## What still verifies nothing

`ReviewMode::Auto`/`Human` still trust the harness's own `is_error` self-report completely — no test run, no build check, no diff-vs-`acceptance_criteria` comparison, regardless of `verify_cmd`. Only `Agent` mode runs anything: `acceptance_criteria` (present in the frontmatter since [Agent handoff](agent-handoff.md)) is first read by `verify_cmd`'s deterministic exit-code check when set, then always by `agent_review`'s LLM judgment of the diff. That LLM judgment itself is still unverified in the sense that matters — a research pass into current agent-completion-signaling practice (2026-08-17, in-session) found that current tools favor deterministic CI/test gates plus PR review over trusting a model's self-report, which is exactly what motivated building `verify_cmd` rather than leaving `Agent` mode as pure LLM-judges-LLM. What `verify_cmd` doesn't close: whether the *diff itself* actually satisfies `acceptance_criteria` beyond "the tests pass" — a green test suite doesn't prove the acceptance criteria were met, only that nothing broke. Also unclosed: lucid doesn't wait on or read back the PR's own CI check runs (if the repo has any configured) before merging under `Auto`/`Agent`-pass — `gh pr merge` is called immediately once the verdict is `CloseAutomatically`, so a slow or still-running CI check isn't a gate today.

## Setup requirements

- **Linear backend**: same pattern as the existing `proposal:*` decision labels — `LinearAdapter::label_id` looks labels up, it never creates them. A Linear workspace using this backend needs `review:auto`, `review:human`, and `review:agent` labels created ahead of time, or `create_proposal` fails outright for any proposal with a non-default review mode — including one filed via `lucid task create --review agent`, which hits the identical failure since it calls `create_proposal` too.
- **`gh` CLI**: required on `PATH` and authenticated against the repo's remote — every dispatch that commits anything pushes and opens/merges a PR through it. `daemon.workdir` must have an `origin` remote reachable by `gh`; without one, `pr::push_branch`/`pr::create` fail and the dispatch's `PrOutcome` becomes `Failed` (routes to `NeedsReview`, not a hard dispatch failure — see the second bug fix above).
